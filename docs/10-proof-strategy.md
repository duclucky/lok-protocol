# 10 — Proof Strategy

This document is written **before** the code it constrains, and reviewed by a human before any Solidity or TLA+ is
produced. It is the most important artefact in the repository, because every downstream tool is only as strong as the
list of propositions here. A tool cannot catch a property nobody asked it to check.

Read this before `docs/02-architecture.md` and `docs/05-contract-specs.md`. Those documents implement what this one
specifies.

---

## 1. What "prove correct" means here

You cannot prove "the system is correct". You can only prove specific, **falsifiable** propositions. The central
discipline of this project is that each proposition is matched to the **kind of evidence that can actually establish
it**. Using the wrong kind produces false confidence:

- Fuzzing cannot prove fairness — it does not know the expected distribution.
- Monte Carlo cannot prove safety — it samples a few paths, not all.
- A closed-form proof cannot establish privacy — leakage lives at the information layer, not the logic layer.
- A model checker cannot prove an invariant it was not given.

So propositions are sorted into four tiers by the strongest evidence available for each, and each tier has one primary
tool and one pass criterion.

## 2. The tiers

| Tier                  | Meaning                                                                                                                                                            | Primary tool                                           | Pass criterion                                                                            |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| **A — closed-form**   | An inductive invariant: true initially, preserved by every transition. Strongest. Reserved for fund safety.                                                        | Foundry invariant/fuzz + a written hand proof          | Invariant holds over ≥ 10⁷ fuzzed action sequences **and** the hand proof is reviewed.    |
| **B — model-checked** | Depends on external behaviour (who reveals, who cranks) but is finite-state. Exhaustively checked over adversary interleavings.                                    | TLA+ / TLC                                             | No counterexample in the model within the configured bounds.                              |
| **C — statistical**   | No closed form exists; correctness is empirical, with an explicit trust boundary to the underlying platform.                                                       | Monte Carlo + chi-squared                              | Empirical result within the stated confidence interval; the trust boundary is documented. |
| **D — adversarial**   | A negative property (nothing leaks). Established by enumerating channels and refuting each. Never provable as "nothing"; only "this specific leak does not occur". | Static analysis + indistinguishability diff + red team | Every enumerated channel has a passing refutation test; residual channels are documented. |

The tier assignment is itself a claim to review. If a proposition is assigned tier A but actually depends on external
behaviour, the proof will be unsound. Challenge the tiering during human review.

## 4. Execution order

The proofs are produced in dependency order. Each stage gates the next.

**Stage 0 — freeze this document.** Human review of §3 for completeness. The question is only "what proposition is
missing?" No code exists yet. This is the one stage AI cannot self-complete, because a model cannot know what its own
spec omits.

**Stage 1 — TLA+ model (`spec/LokDraw.tla`).** Encode the dual-mode state machine (including the commit-reveal reveal
phase and timeouts), pause/config transitions, the participant actions callable in every state, the two-counter solvency
checkpoint lifecycle, and an adversary that can withhold or conditionally reveal, stop cranking, spam abort, submit
forged/stale inputs, and reorder its own transactions. Model the oracle as possibly-permanently-down. Check P-L1..P-L7,
P-S7, P-F3, P-F10, P-A4, P-A7, P-A8, and P-O1. For B + A rows, TLC checks only the state-machine half; Foundry,
integration, or boundary-test obligations remain in their assigned stages. P-L6 additionally requires its boundary test.
A counterexample here is a **design** fix, made before any Solidity is written. This is the highest-leverage stage: it
is cheap and it shapes the contracts.

**Stage 2 — contract skeletons to satisfy the checked model.** Write `LokVault`, `LokDrawManager`, `LokGuardian` so
their state machine is a refinement of the TLA+ model. Where the contract adds detail the model abstracts, note the
abstraction gap explicitly.

**Stage 3 — tier-A invariant proofs.** Discharge P-S1..P-S9, the A-half of P-L5, P-F2/P-F5/P-F6/P-F7/P-F9,
P-A1..P-A4/P-A6/P-A8, and the A-half of P-O1 with their assigned Foundry, unit, boundary, integration, and hand-proof
tools. Written hand proofs for P-S2 and P-S3 are reviewed alongside. Fuzz the applicable reference invariants to ≥10⁷
sequences using the full team's compute budget.

**Stage 4 — differential testing.** Two independently written implementations of `_syncUser` and the draw core, from
this spec, run against the same fuzz vectors. Any divergence is a bug or a spec ambiguity — both are findings. The two
implementations must be written by teams that do not share context.

**Stage 5 — tier-C fairness.** Monte Carlo for P-F1 and P-F1', with P-F2's hand proof reviewed and P-F4's trust boundary
written into the README.

**Stage 6 — tier-D privacy.** Discharge P-P1/P-P2/P-P4..P-P9 with their assigned log-diff, static ABI/ACL/allowlist,
gas/HCU, analysis, and human-review tools. P-P9's UX half remains explicitly human-reviewed. Then run a red-team pass
whose only job is to find a channel not in the list.

**Stage 7 — human audit of the boundary.** A person re-reads §3 and §5 and asks what is assumed rather than proven. This
closes the gap no compute can close.

## 5. Trust boundary — stated, not hidden

After every proof above, exactly these assumptions remain. They are not Lok's design choices; they bound Lok's
guarantees, and stating them precisely is itself part of being trustworthy.

| Assumption                                                                           | Why it remains                                                                                  | Mitigation in Lok                                                                                                                                                          |
| ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Raw `FHE.rand` is uniformly distributed.                                             | A cryptographic guarantee of the Zama platform; not reprovable at the application layer (P-F4). | None needed; documented as a platform trust boundary.                                                                                                                      |
| The KMS committee (13 nodes, 2/3) does not collude to decrypt `r` before settlement. | Threshold cryptography; collusion above threshold is possible in principle.                     | Strict mode (I13): XOR of `FHE.rand` with committed participant entropy means one honest participant defeats KMS collusion. This is why branch-1 puts strict mode in core. |
| Coprocessor majority is honest.                                                      | Consensus assumption of the platform.                                                           | Not reprovable here, but every FHE op is publicly recomputable, so one honest verifier detects a dishonest majority after the fact.                                        |
| The yield source does not fail.                                                      | Adapter risk is depositor risk.                                                                 | "No-loss" holds under normal operation of the venue, exactly as for comparable prize-savings protocols. Documented, not implied away.                                      |
| The host chain's signature scheme and the input ZK proof are not post-quantum.       | Platform-level.                                                                                 | Documented.                                                                                                                                                                |
| No leakage channel exists beyond S1–S8.                                              | Privacy is a negative; unenumerated channels cannot be excluded by any tool.                    | Human red team (Stage 6/7); this is the irreducible residue.                                                                                                               |

A submission that draws this boundary sharply is more credible than one claiming unconditional guarantees. Reproduce
this table in the README's threat-model section.

## 6. What this strategy cannot do

State this plainly, to the team and in the README:

- It cannot prove the absence of a leakage channel nobody enumerated (P-P set is a floor, not a ceiling).
- It cannot prove the Zama platform's cryptographic guarantees; it inherits them (P-F4 and §5).
- It cannot compensate for a missing proposition in §3. **The human review at Stage 0 is load-bearing and
  irreplaceable.** No amount of compute substitutes for a person asking "what did we forget to require?"
- The team writing an implementation cannot be the team proving it correct, or the proof inherits the implementation's
  blind spots. Separation of the two is a hard rule, not a preference.
